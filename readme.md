## Project Overview

This project implements an end-to-end machine learning pipeline for detecting phishing websites using a dataset of 10,500 websites with 15 features. The pipeline achieves **F1 scores of 0.80 - 0.81** through strategic feature selection, model-specific optimization, and evidence-based design decisions from comprehensive exploratory data analysis (EDA).

### Key Achievements:

- ✅ **Top 10 Feature Selection** - Uses only the most discriminative features (from 36-41 engineered features)
- ✅ **Model-Specific Feature Sets** - Tree models get polynomial features, linear models avoid multicollinearity
- ✅ **Feature-Specific Outlier Handling** - Preserves phishing signatures while cleaning data errors
- ✅ **Target Encoding** - Captures HostingProvider's strong signal (χ²=1739) in a single feature
- ✅ **F1 Score: 0.80-0.815** - Balanced precision and recall for security context

## Key EDA Findings and Design Decisions

*Summary of insights from `eda.ipynb`. Full details available in the Jupyter notebook.*

### 1. Dataset Characteristics

| Characteristic | Value | Implication |
|---------------|-------|-------------|
| **Total Samples** | 10,500 | Large enough for robust training |
| **Class Distribution** | 45% phishing, 55% legitimate | Slight imbalance → use `class_weight='balanced'` |
| **Features** | 15 original | Need feature engineering |
| **Missing Values** | LineOfCode: 22.43% | Requires imputation strategy |

### 2. Top 10 Features (From Statistical Analysis)

| Rank | Feature | Metric | Value | Interpretation |
|------|---------|--------|-------|----------------|
| 1 | **HostingProvider** | χ² | 1739.12 | Free hosting 3.5× more phishing than enterprise |
| 2 | **HasExternalRefs** | r | 0.3814 | Engineered - sites without external links suspicious |
| 3 | **IsResponsive** | φ | 0.3298 | 77% legit vs 45% phishing are responsive |
| 4 | **DomainAgeMonths** | r | 0.3329 | Legitimate domains 2× older (43 vs 21 months) |
| 5 | **Industry** | χ² | 412.90 | Banking 64% phishing vs Food 29% |
| 6 | **DomainAge_Squared** | r | 0.2570 | Non-linear aging effect (tree models only) |
| 7 | **Robots** | φ | 0.2413 | Sites with robots.txt 3× more likely legitimate |
| 8 | **NoOfiFrame** | r | 0.1496 | More iFrames → legitimate (payment processors) |
| 9 | **TotalReferences** | r | 0.1423 | Engineered - total linking activity |
| 10 | **NoOfExternalRef** | r | 0.1281 | Better connectivity → legitimate |

**Alternative #10 for Linear Models:** HasPopups (r=0.1178) - replaces DomainAge_Squared to avoid multicollinearity

### 3. Critical Design Decisions

#### Decision 1: Top 10 Features Only (Not All 36-41)

**Reasoning:**
- Pareto Principle: Top 10 capture ~85-90% of discriminative power
- Remaining features: r < 0.10 (weak) or not significant
- Curse of dimensionality: More features ≠ better performance, reduces overfitting

#### Decision 2: Model-Specific Feature Selection

**Problem:** DomainAgeMonths and DomainAge_Squared are highly correlated (r ≈ 0.95)

**Solution:**
- **Tree models (RF, XGBoost, GB):** Use BOTH features
  - Reason: Trees immune to multicollinearity (no matrix inversion)
  - Benefit: Captures non-linear aging effect
- **Linear models (LR, SVM):** Use ONLY DomainAgeMonths
  - Reason: Avoid variance inflation (VIF > 10)
  - Benefit: Stable, interpretable coefficients

**Implementation:** `preprocessor.get_features_for_model(X, model_name)` automatically selects appropriate features

#### Decision 3: Target Encoding for HostingProvider

**Why not one-hot encoding?**

| Aspect | One-Hot | Target Encoding ✅ |
|--------|---------|-------------------|
| Features created | 12 columns | 1 column |
| Signal preservation | Indirect | Direct (phishing probability) |
| χ² statistic | 1739 (same) | 1739 (same) |
| Interpretability | High | Medium |

**HostingProvider Risk Tiers:**
- Very High Risk (70-73%): Freehostia, InfinityFree, 000webhost → Encoded: 0.27-0.30
- Very Low Risk (20-24%): AWS, Azure, Google Cloud → Encoded: 0.76-0.79
- **3.5× phishing rate difference!**

**Decision:** Target encoding preserves this massive signal in a single feature

**Why one-hot for Industry?**
- Lower χ² (413 vs 1739) - moderate signal
- More balanced risk distribution (2.2× vs 3.5×)
- Interpretability valuable: "Banking sites risky" > "Industry encoding = 0.36"

#### Decision 4: Feature-Specific Outlier Handling

**Problem:** Blanket outlier removal eliminates phishing signatures

**Solution - 4-Tier Strategy:**

| Tier | Features | Strategy | Reason |
|------|----------|----------|--------|
| **Protected** | NoOfPopup, NoOfiFrame, NoOfURLRedirect | NO treatment | Outliers ARE the phishing signal |
| **Extreme Clip** | NoOfImage | 99th percentile | Data quality issue (skewness 102.47) |
| **Conservative** | NoOfSelfRef, NoOfExternalRef, LargestLineLength | 3×IQR | Preserve legitimate variation |
| **Standard** | Others | 1.5×IQR | Normal outlier treatment |

**Evidence:**
- NoOfPopup outliers (>100 popups) → 95% phishing
- NoOfiFrame outliers (>50 iFrames) → Phishing attack vectors
- Removing these = losing discriminative power!

#### Decision 5: Missing Value Strategy

**LineOfCode: 22.43% missing**

**Solution:**
1. Create binary indicator: `LineOfCode_IsMissing` (captures missingness pattern)
2. Impute with median (robust for skewed data)

**Why not mean?**
- LineOfCode is heavily skewed (phishing: 543, legitimate: 1718)
- Median (1018) more representative than mean

**Why not drop?**
- Would lose 2,350 samples (22% of data)
- Missingness itself may be informative (phishing sites less complex)

### Model Comparison Strategy

**Evaluation Priority (Security Context):**
1. **F1 Score** (PRIMARY) - Balance precision and recall
2. **Recall** (CRITICAL) - Minimize false negatives (missing phishing = user compromise)
3. **ROC-AUC** (HIGH) - Overall discrimination ability
4. **Precision** (MODERATE) - Minimize false positives (user annoyance)
5. **Accuracy** (LOW) - Can be misleading with class imbalance

**Selection Criteria:**
- Best F1 score on validation set
- If F1 scores within 0.5%, choose model with higher recall
- Consider model complexity for deployment

## Evaluation Metrics

### Metrics Calculated

#### 1. Confusion Matrix

```
                 Predicted
              Phishing | Legitimate
        ─────────────────────────────
Actual  Phishing  |   TP   |   FN   |
        Legitimate|   FP   |   TN   |
        ─────────────────────────────
```

**Interpretation:**
- **TP (True Positives):** Correctly identified phishing sites
- **TN (True Negatives):** Correctly identified legitimate sites
- **FP (False Positives):** Legitimate sites flagged as phishing (annoying but safe)
- **FN (False Negatives):** Phishing sites missed (DANGEROUS - users compromised!)

**Priority:** Minimize FN > Minimize FP

#### 2. Accuracy

```
Accuracy = (TP + TN) / (TP + TN + FP + FN)
```

**Use Case:** Overall correctness  
**Limitation:** Misleading with class imbalance  
**Priority:** LOW

#### 3. Precision

```
Precision = TP / (TP + FP)
```

**Meaning:** Of all flagged phishing sites, how many were actually phishing?  
**High Precision:** Few false alarms  
**Priority:** MODERATE (user experience consideration)

#### 4. Recall (Sensitivity)

```
Recall = TP / (TP + FN)
```

**Meaning:** Of all actual phishing sites, how many did we catch?  
**High Recall:** Few phishing sites slip through  
**Priority:** CRITICAL (security is paramount)

#### 5. F1 Score

```
F1 = 2 × (Precision × Recall) / (Precision + Recall)
```

**Meaning:** Harmonic mean of precision and recall  
**Use Case:** Balanced metric for imbalanced data  
**Priority:** PRIMARY (used for model selection)

#### 6. ROC-AUC

**ROC Curve:** True Positive Rate vs False Positive Rate at various thresholds  
**AUC:** Area Under the ROC Curve (0.5 = random, 1.0 = perfect)

**Meaning:** Model's ability to discriminate between classes  
**Use Case:** Compare models, assess discrimination ability  
**Priority:** HIGH (secondary to F1)

### Why These Metrics?

**Security Context:**
- **False Negative = User compromised** → Minimize through high recall
- **False Positive = User annoyed** → Minimize through decent precision
- **F1 balances both** → Primary metric for model selection

**Not Using:**
- Accuracy alone: Misleading with 45/55 split
- Precision alone: Could achieve 100% by flagging everything (terrible recall)
- Recall alone: Could achieve 100% by flagging everything (terrible precision)

### Critical Performance Insights

#### 1. Why Lower Than Expected (0.81 vs 0.93-0.96)?

**Hypothesis 1: Data Quality Issues**
- Original EDA was on full dataset; actual performance reflects real-world noise
- Label quality: Some "legitimate" sites might be phishing and vice versa
- Feature quality: HTMLCode-based features (LineOfCode, NoOfImage) may be noisy

**Hypothesis 2: Class Overlap**
- Phishing sites increasingly mimic legitimate sites
- 45/55 class split with ~20% misclassification suggests inherent difficulty
- Some features (e.g., Industry, IsResponsive) have overlapping distributions

**Hypothesis 3: Feature Engineering Limitations**
- TotalReferences dominates (60-80% importance in boosting models)
- Other features contribute minimally
- May need domain-specific features (URL patterns, SSL cert age, etc.)

**Hypothesis 4: Overfitting in EDA**
- Initial correlation estimates may have been inflated
- Cross-validation in production reveals true generalization

**Observation:**
- XGBoost: 60% importance

### Feature Engineering Insights

#### What Worked Well:

1. **TotalReferences** (Engineered)
   - **Strongest feature** across all models
   - Simple aggregation (NoOfSelfRef + NoOfExternalRef)
   - Lesson: Sometimes simple aggregations beat complex transformations

2. **DomainAge_Squared** (Polynomial)
   - Captures non-linear aging effect
   - Tree models use it effectively (4-8% importance)
   - Correctly excluded from linear models (multicollinearity)

3. **Target Encoding for HostingProvider**
   - Condensed 13 categories → 1 feature
   - Retained discriminative power (5-9% importance)
   - Better than one-hot (would be 12 features)

#### What Underperformed:

1. **HasExternalRefs** (Binary flag)
   - Expected: r=0.38 (2nd strongest from EDA)
   - Actual: Minimal importance (<1%)
   - **Why**: Captured by NoOfExternalRef and TotalReferences

2. **IsResponsive** (Binary)
   - Expected: φ=0.33 (3rd strongest)
   - Actual: Minimal importance (<1%)
   - **Why**: May correlate with DomainAge or Industry

3. **Robots** (Binary)
   - Expected: φ=0.24
   - Actual: <1% importance
   - **Why**: Modern phishing sites may include robots.txt to appear legitimate

**Lesson Learned:**
**Univariate** correlation (from EDA) ≠ **multivariate** importance (in models)

Features that look strong individually may be redundant when combined.

- ❌ Lower precision (more false alarms)

**Business Decision:** How much user annoyance is acceptable to prevent compromises?

### 3. Model Monitoring

**Track in Production:**
- **Prediction distribution** - Are we flagging 45% as phishing (like training)?
- **Feature drift** - Are hosting providers changing?
- **Performance metrics** - Weekly F1 score on labeled samples
- **New categories** - Unknown hosting providers, new industries

**Red Flags:**
- Phishing rate drops below 30% → Model may be missing new techniques
- New HostingProvider appears frequently → Update target encoding
- F1 score drops > 5% → Retrain model

### 4. Retraining Strategy

**Triggers for Retraining:**
- Performance degradation (F1 < 0.80)
- New phishing techniques emerge
- Quarterly scheduled retraining
- Significant feature drift detected

**Process:**
1. Collect new labeled data (1,000+ samples)
2. Combine with existing training data
3. Re-run EDA to validate top 10 features still hold
4. Retrain all models
5. A/B test new model vs old model
6. Deploy if new model F1 > old model F1 + 1%
